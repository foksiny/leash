Concurrency Model

Mental model

Leash supports multi-threaded programming through workers — special functions that run concurrently in separate OS threads. Ordinary code runs on one thread; a worker is a unit of work you hand to the runtime. Workers do not share function locals: each thread has its own stack. They communicate through two kinds of module-wide variables, shared and fusion, or they can return a value through an async fnc future.

Workers

A worker fnc is a function the runtime can start on its own OS thread. Spawn one for each independent stream of work.

Shared state

shared is one-writer, many-reader; fusion allows every thread to read and write with atomic scalar updates.

Futures

async fnc returns a future<T> immediately. await joins it and yields the typed result.

Three ways to run concurrently. Use spawn for fire-and-forget workers, async fnc + await when you need a result, and shared/fusion globals for state that several threads observe. They all use the same worker machinery under the hood.

Worker functions

Mark a function with worker fnc instead of fnc to make it runnable in its own OS thread. Workers are declared just like regular functions, accept parameters normally, and typically run in a loop — checking thisworker.interrupted to know when the program is shutting down.

  • Workers are declared like regular functions but with the worker keyword
  • They accept parameters like normal functions
  • They run in an infinite loop by default
  • Use thisworker.interrupted to check if the program is shutting down
Workers are not started by declaration. A worker fnc is just a callable body until you spawn it (or it is invoked as the body of an async fnc call). Declaring one does not create a thread.

Spawning workers

Use spawn to launch a worker function in a new OS thread. Each spawn call creates a dedicated thread, passes arguments by value (copied into a heap-allocated struct), and starts execution immediately. Spawned threads run concurrently with main and with each other.

  • Each spawn creates a new OS thread running the given worker function
  • Arguments are passed by value (copied into a heap-allocated struct)
  • All spawned threads run concurrently with main and with each other
  • Workers stop when the program terminates or when thisworker.interrupted becomes true (for example on Ctrl+C)

spawn is fire-and-forget: it gives you no handle and no result. For a value, use async/await instead. spawn cannot be used on an async fnc — that call already runs on a worker.

Shared variables (shared)

A shared variable allows one thread to write while any number of threads read. This is the default safe pattern for producer-consumer scenarios where a single worker produces data and multiple workers consume it. Since only one writer is allowed, there is no risk of write-write conflicts, making shared the simplest and safest choice for one-to-many communication patterns.

The one-writer rule is enforced at compile time: assigning to a shared variable (including through an element or field write) from two different functions is an error — use a fusion variable instead if several workers must write it.

PropertyDescription
WritersOnly one worker may write at a time
ReadersAny number of workers may read
AtomicityNo guarantees — readers may see stale values
Not the same thing as a function shared variable. The shared keyword declares a module-wide variable that every function in the module can see — it exists for worker communication, and the one-writer rule keeps concurrent access safe. Leash also has function shared variables, declared in a function signature (fnc f() : void | result: int): those are program-wide storage too, but only the functions that declare them may touch them, and they carry no thread-safety rules at all. See Shared Variables in the language guide for the full comparison.

Fusion variables (fusion)

A fusion variable allows multiple threads to both read and write concurrently. Scalar integer fusion variables compile to atomic (sequentially consistent) loads and stores, and the counter idiom counter = counter + n lowers to a single atomic read-modify-write, so concurrent updates never lose increments. This makes fusion the right choice for counters, flags, and coordination variables that many threads need to share and update. Sub-byte values (such as bool) and composite values (arrays, vectors, structs) do not have atomic forms and keep plain access.

Async, await & futures

Where spawn is fire-and-forget, async/await gives you a value back. Declare a function with async fnc and calling it returns a future<T> handle immediately — the body runs on a worker thread. await joins the future and yields the result T.

fnc heavy_computation(user string) : int {
    return user.size * 10;
}

async fnc fetch_score(user string) : int {
    // runs on a worker thread
    return heavy_computation(user);
}

fnc main() : void {
    // three tasks in flight at once — real parallelism
    a: future<int> = fetch_score("ada");
    b: future<int> = fetch_score("linus");
    c: future<int> = fetch_score("grace");

    show(await a, await b, await c);  // joins in any order
}

Async functions compose. An async fnc may call (and await) other async functions — including itself, where recursion spawns child tasks. Calling an async function from inside its own body is always a new task; use await to collect results. spawn cannot be used on an async function (it already runs on a worker), and main cannot be async.
Worker cap. The runtime runs at most 64 worker threads. Creating a 65th task does not deadlock and does not lose the result: the extra task runs inline on the calling thread, so its future still completes (you lose only the parallelism, and the runtime prints a notice). A future you never await stays rooted until the process exits, so fire-and-forget tasks are fine for a bounded number of calls, not an unbounded loop.

The thisworker built-in

Inside a worker body, thisworker gives the running thread a handle on its own shutdown state. Polling it is the cooperative way to exit a long-running loop cleanly.

interruptedbooltrue when program is shutting down (for example, Ctrl+C)

Full example

Put together: a shared value with a single writer, a fusion counter with atomic increments, three workers, and a main that spawns them.

shared result: int = 0;
fusion counter: int = 0;

worker fnc calculate(a int, b int) : void {
    while !thisworker.interrupted {
        result = a + b + result;
        show("calculate updated result to: ", result);
    }
}

worker fnc increment_counter() : void {
    while !thisworker.interrupted {
        counter = counter + 1;
        show("counter incremented to: ", counter);
    }
}

worker fnc show_result() : void {
    while !thisworker.interrupted {
        show("result:", result, " counter:", counter);
    }
}

fnc main() : void {
    spawn calculate(3, 5);
    spawn increment_counter();
    spawn show_result();
}

Lifecycle & cleanup

Declaration

A worker fnc is compiled like any function but flagged as thread-capable. No thread exists yet.

Start

Workers are automatically started when spawn is called (or when an async fnc call is made). Arguments are copied into a private transfer block.

Run

They run until the program exits or thisworker.interrupted is true. Ctrl+C sets the interrupted flag for clean shutdown.

Join

Futures are joined with await; the runtime waits for all workers to finish before full exit. There is no explicit thread-join API for spawn.

Reclaim

Worker scope allocations use each thread's arena; root objects are published process-wide when workers spawn (in `--gc` builds the collector handles them instead); each worker's private arena/GC state is released when its thread exits.

Pitfalls

Two writers to one shared variable. Assigning to a shared global — including through an element or field write — from two different functions is rejected at compile time. Split the value into one variable per writer, or switch the variable to fusion if it is a scalar integer.
Expecting shared reads to be fresh. There is no atomicity guarantee: readers may observe stale values. If you need a counter or flag that several threads update, use fusion.
Busy loops with no exit check. A worker that loops forever without consulting thisworker.interrupted prevents a clean shutdown. Check the flag on each iteration.
Unbounded fire-and-forget futures. An unawaited future<T> stays rooted until process exit. Bounded call counts are fine; an unbounded loop of async calls without await grows memory.
Interleaved output is normal. show() is thread-safe, but lines from different workers can appear in any order. Do not read sequencing into the printed output.

Frequently asked questions

QuestionAnswer
How do I get a result back from a worker?Use async fnc and await; spawn is fire-and-forget and returns no handle.
Can two workers increment the same variable?Yes, if it is a scalar fusion integer. counter = counter + n is one atomic read-modify-write, so no increments are lost.
Can I spawn an async function?No. Every async fnc call already runs on a worker; just call it and await the returned future.
Can main be async?No. main stays a plain function; it can create and await futures.
What happens after 64 workers?The next task runs inline on the calling thread. Its future still completes; only the parallelism is lost.
Are there mutexes or locks?Not built in. Coordinate with fusion variables (atomic scalar updates) instead.
Is shared the same as a function-shared variable?No. shared is module-wide and has the one-writer rule; function-shared variables are declared in signatures, visible only to functions that declare them, and carry no thread-safety guarantees.
Is allocation from a worker safe?Yes — the GC is thread-safe. Native threads created outside Leash (FFI callbacks) must call leash_gc_thread_attach() first.
