Known Limitations

Severity at a glance

Only four areas have known, documented limits. Two are platform-maturity notes (🟢 low severity), one is a deliberate non-goal (🟢 low), and one is the genuine trade-off you must understand when using the default memory layout (🟠 medium). Nothing here is an unknown crash waiting to happen in ordinary code.

Scoped arena ownership — the one real trade-off

The arena backend is the default for native leash compile and leash run. It provides deterministic bump allocation with whole-scope and per-iteration reclamation, no GC pauses or scans, and C-ABI-friendly plain pointers. It is often leaner and faster on allocation-churn and hash/string-heavy workloads (especially with O2+ reserves/pre-sizing and O3+ compact nodes/fused keys), but it is not a universal win: growth-heavy kernels can retain superseded buffers until scope reset, and tiny compute-bound cases may show noisy or negligible deltas. The JVM target always uses its own GC and does not accept arena flags.

Lifetime model

No borrow checker. Pointers are valid until the allocating frame/iteration exits. Returns and spawned/async data escape by copy or into the root arena; spawn uses the compiler's type tree to root nested fields, and unions transfer as boxed values with their real size.

Compile-or-fail audit

Only unprovable raw-pointer escapes are errors — there is no warning-only outcome. Libc heap calls, proven-safe returns, raw-pointer globals and stores, and proven worker arguments are accepted. Header readers validate the allocation tag, containment and block-bounded sizes, so forged or stale pointers abort instead of reading out of bounds.

Root arena

A value that outlives its frame is copied into the program-lifetime root arena, which is never rewound. The slot reuses its copy while it is the only owner, so assigning the same global in a loop keeps a constant footprint. Stats report scope and root arenas separately.

Spawn hand-off

Arguments are copied into one compact private transfer block; strings travel through it, containers and aggregates keep their root copies, and the worker releases the transfer immediately after unpacking.

The known ownership caveat

Raw pointers returned from native (FFI) code are proven-safe: a runtime check aborts if such a pointer points into an arena frame. Union payloads with heap variants are rooted before boxing. Escaping &x pointees are root-allocated (or made immortal in worker programs), and both the slot and its value are rooted so strings, vectors and structs stay valid after the producing frame pops. Libc heap pointers are foreign and provenance-checked. A pointer keeps its provenance through local copies, so proven-safe returns, globals, long-lived stores and worker arguments are accepted; only pointers whose origin cannot be proven are rejected. The runtime publishes root blocks to every worker's block index and keeps them alive while workers exist, so container, class and heap-field struct pointees are safe to share across threads as well.

One accepted difference from GC

A mutable container stored into a global re-points the source local at the global's root copy, so g = v; g.pushb(4) is visible through both names. After g = v; g = X the arena reuses the global's root copy in place, so v observes X's contents; GC mode keeps v pointing at the old vector. Strings are immutable/copy-on-write and are never re-pointed this way. This is the only intentional observable difference between the two native memory modes.

Safety defaults

  • Poison on reclaim: reclaimed memory is filled with 0xDD by default (LEASH_ARENA_POISON=0 disables).
  • Frame-exit verification: before every scope pop or loop reset, registered global/shared/static pointer slots are checked for pointers into the frame being reclaimed (LEASH_ARENA_VERIFY=0 disables this default-on check). A missed root copy becomes a loud abort instead of a silent dangling pointer.
  • Escape snapshots: bounded byte snapshots of reclaimed blocks are enabled by default (LEASH_ARENA_ESCAPE_SNAPSHOT=0 disables), invalidated on address-range reuse, and shared by every staging read through one snapshot image.
  • Frame/loop misuse: underflow, over-depth exit, and invalid or out-of-range frame operations abort with diagnostics.
  • Deep escapes: nested heap fields in returned structs/classes are deep-staged and committed across pops; recursive aggregate returns copy the reachable graph with an identity map so cycles survive. Value-copy cloning of a recursive struct is bounded at eight type levels — deeper pointer chains keep sharing the tail pointer, which is safe but not a full deep copy.
  • Frameless paths: allocation-free functions and loops may skip framing only when allocation analysis can prove it.

Measurement

Use LEASH_ARENA_STATS=1 for the scope/root peak block bytes and payload. For a fair GC-vs-arena comparison, clear ~/.leash/shcache, interleave runs, and record CPU and max RSS via /usr/bin/time -v — RSS is page-granular, so block-byte peaks are the more honest allocator metric.

# Observe both arenas at shutdown
LEASH_ARENA_STATS=1 leash run myprogram.lsh

# Opt out of the default when ownership cannot be modelled
leash run myprogram.lsh --gc

Windows serve_tls is experimental

The httpserver module's TLS listener, serve_tls(port, cert, key, handler) (and serve_tls_ex), is available on every supported platform. On Linux, Linux ARM64 and macOS the shim uses BSD sockets plus OpenSSL and ALPN negotiates h2 or HTTP/1.1 per connection. On Windows the shim uses the system SChannel stack (no external dependency): the key must be an RSA key in PEM form (PKCS#8 BEGIN PRIVATE KEY or PKCS#1 BEGIN RSA PRIVATE KEY) and the listener speaks HTTP/1.1 over TLS — Windows ALPN is not wired up, so h2 clients fall back to HTTP/1.1.

The Windows arm is cross-compiled with MinGW-w64 and exercised under Wine in CI; it has not yet been battle-tested on real Windows hosts, so treat it as experimental for now. Plain HTTP on Windows has no such caveat, and the Linux/macOS TLS path is the same mature OpenSSL shim used elsewhere. See installthis/httpserver/README.md for the per-platform matrix.

JVM sql is a mini engine, not SQLite

All three former @from-only stdlib modules now work on the JVM target through bundled Java shims (source under leash/jvm/, prebuilt .class files shipped with the runtime, the same policy as the liblsh*.a archives):

http

Rides java.net.http: same request API, redirect rules, error codes (LSH_E_*), strerror text, leash-http/1.1 user agent, binary-safe downloads and TLS (with the verify_tls opt-out). *_h2 calls negotiate h2 over TLS via ALPN and fall back to HTTP/1.1; cleartext h2c prior-knowledge is unavailable, so cleartext *_h2 calls report proto = "http/1.1".

httpserver

Rides jdk.httpserver: same serve/serve_ex/serve_tls API, handler contract, reply_* helpers, response context, shutdown() semantics (stops after the current response), request quotas and LSHD_E_* error codes. HTTP/1.1 only (no h2/h2c); RSA keys in PEM form.

sql

Rides a small SQL interpreter (leash/jvm/LeashSql.java), not SQLite. The lsql_* contract is faithful: sqlite3 result codes, column-type numbering, prepare-time metadata, reset() keeping bindings, changes()/last_insert_rowid(), INTEGER PRIMARY KEY rowid aliasing, transactions, and SQLite type affinity.

What the JVM SQL subset supports

CREATE TABLE, INSERT, SELECT (columns, *, COUNT(*), WHERE, ORDER BY [DESC]), UPDATE, DELETE, DROP TABLE and transactions with ? parameters. The stdlib test program (tests/stdlib/sql_sqlite.lsh) produces byte-identical output on the JVM and natively.

The two honest caveats. Expressions beyond the surface above — joins, subqueries, indexes, GROUP BY — are not available, and database files use the engine's own line format (LEASHSQL1 magic), not sqlite3 files. Opening an existing sqlite3 file on the JVM fails cleanly, and a JVM-written file is “not a database” to native SQLite. Use :memory: or files written by the same engine.

Runtime notes

Function values needed to pass handlers around are supported on the JVM: fnc(...) types lower to single-method interfaces (the handler shape to the shim's LshHttpHandler, anything else to a generated <Main>_LshFn<n>), and &fname lowers to a generated adapter class, so &handler_fn locals, parameters and indirect calls work.

The JVM shims ride java.net.http (JDK 11+), so programs using http or httpserver on the JVM need a Java 11+ runtime; sql itself has no such floor. Programs that use none of the shims keep the JVM target's usual Java 5 class-file floor. Minor engine differences are inherent to the JDK for the web modules: response header casing/order follows the JDK (lookups stay case-insensitive), and the server's own Date/keep-alive handling replaces the C engine's.

HTTP/3 and QUIC

Neither the http client nor the httpserver speaks HTTP/3 or QUIC. HTTP/1.1 and HTTP/2 (h2c and h2-over-TLS) are fully supported on native, and the JVM shims cover the HTTP/1.1 and h2-over-TLS subset described above. HTTP/3 is a deliberate non-goal for the 2.x series, not an oversight — it would require a QUIC transport stack that does not fit the dependency-free design of the web modules.

An E_ARENA_LIFETIME error for a cross-frame storeReturn the value instead, keep it in root/persistent storage, or build that program with --gc.

What is stable

It is easier to list what is not covered than what is. The following are stable, supported contracts in 2.0.0 and are not “limitations”:

The toolchain

Self-hosted compiler, bootstrap from a checked-in seed with no Python, fixed-point verification, and the 89/89 output-parity corpus.

Both native memory modes

Arena by default and mark-and-sweep via --gc, with identical program output. --autofree, nogc and the JVM's own GC are stable alternatives.

Core language and libraries

Types, generics, unions, classes, async/await, workers, the file API, the full standard library and the package manager.

Web stack on native

HTTP/1.1 and HTTP/2 (h2c + h2-over-TLS) for client and server, plus the TLS listener on Linux, Linux ARM64 and macOS.

Reporting a limit

Documented here deliberately: shipping a compiler means being explicit about what it does not do. If any of these becomes important, or you find a lifetime pattern the audit should model but does not, open an issue at github.com/foksiny/leash with a minimal reproducer and the memory mode you used.
