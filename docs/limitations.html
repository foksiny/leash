Known Limitations

Leash 1.6.1 is a complete, self-hosted toolchain: the compiler is written in Leash, builds itself from a checked-in bootstrap seed with no Python, and passes an 89/89 output-parity corpus. The items below are the honest, currently-known limits of the platform — each is intentional, scoped, and stable for 1.x.

LimitationSeverityComment
Windows serve_tls is experimental 🟢 Low SChannel backend; cross-compiled and exercised under Wine, not yet battle-tested on real Windows.
JVM sql is a mini engine, not SQLite 🟢 Low Same API and semantics for the supported subset; own file format, so sqlite3 files don't open.
HTTP/3 / QUIC 🟢 Low Not implemented, but nobody expects it in 1.x.

Windows serve_tls is experimental

The httpserver module's TLS listener, serve_tls(port, cert, key, handler) (and serve_tls_ex), is available on every supported platform. On Linux, Linux ARM64 and macOS the shim uses BSD sockets + OpenSSL and ALPN negotiates h2 or HTTP/1.1 per connection. On Windows the shim uses the system SChannel stack (no external dependency): the key must be an RSA key in PEM form (PKCS#8 BEGIN PRIVATE KEY or PKCS#1 BEGIN RSA PRIVATE KEY) and the listener speaks HTTP/1.1 over TLS — Windows ALPN is not wired up, so h2 clients fall back to HTTP/1.1. The Windows arm is cross-compiled with MinGW-w64 and exercised under Wine in CI; it has not yet been battle-tested on real Windows hosts, so treat it as experimental for now. See the installthis/httpserver/README.md for the per-platform matrix.

JVM sql is a mini engine, not SQLite

All three former @from-only stdlib modules now work on the JVM target through bundled Java shims (source under leash/jvm/, prebuilt .class files shipped with the runtime, the same policy as the liblsh*.a archives):

  • http — rides java.net.http: the same request API, redirect rules, error codes (LSH_E_*), strerror text, leash-http/1.1 user agent, binary-safe downloads and TLS (with the verify_tls opt-out). *_h2 calls negotiate h2 over TLS via ALPN and fall back to HTTP/1.1; h2c prior-knowledge is not available (the JDK client has no cleartext h2), so cleartext *_h2 calls report proto = "http/1.1".
  • httpserver — rides jdk.httpserver: same serve/serve_ex/serve_tls API, handler contract, reply_* helpers, response-body/header context, shutdown() semantics (stops after the current response), request quotas and LSHD_E_* error codes. The listener speaks HTTP/1.1 only (no h2/h2c), and accepts RSA keys in PEM form (PKCS#8 or PKCS#1).
  • sql — rides a small SQL interpreter (leash/jvm/LeashSql.java), not SQLite. The lsql_* contract is faithful: sqlite3 result codes (OK/ROW/DONE), column-type numbering, prepare-time column metadata, reset() keeping bindings, changes()/last_insert_rowid(), INTEGER PRIMARY KEY rowid aliasing, BEGIN/COMMIT/ROLLBACK, and SQLite's type-affinity rules for storage and comparisons. The supported surface is CREATE TABLE, INSERT, SELECT (columns, *, COUNT(*), WHERE, ORDER BY [DESC]), UPDATE, DELETE, DROP TABLE and transactions with ? parameters. The stdlib test program (tests/stdlib/sql_sqlite.lsh) produces byte-identical output on the JVM and natively.

The two honest caveats for JVM sql: expressions beyond the surface above (joins, subqueries, indexes, GROUP BY) are not available, and database files use the engine's own line format (LEASHSQL1 magic) — they are not sqlite3 files. Opening an existing sqlite3 file on the JVM fails cleanly (and a JVM-written file is "not a database" to native SQLite). Use :memory: or files written by the same engine.

Function values needed to pass handlers around are supported on the JVM: fnc(...) types lower to single-method interfaces (the handler shape to the shim's LshHttpHandler, anything else to a generated

_LshFn), and &fname lowers to a generated adapter class, so &handler_fn locals, parameters and indirect calls work.

Runtime note: the JVM shims ride java.net.http (JDK 11+), so programs using http/httpserver on the JVM need a Java 11+ runtime; sql itself has no such floor. Programs that use none of the shims keep the JVM target's usual Java 5 class-file floor. Minor engine differences are inherent to the JDK for the web modules: response header casing/order follows the JDK (lookups stay case-insensitive), and the server's own Date/keep-alive handling replaces the C engine's.

HTTP/3 / QUIC

Neither the http client nor the httpserver speaks HTTP/3 or QUIC. HTTP/1.1 and HTTP/2 (h2c and h2-over-TLS) are fully supported; HTTP/3 is a deliberate non-goal for the 1.x series.

Documented here deliberately: shipping a compiler means being explicit about what it does not do. If any of these becomes important, open an issue at github.com/foksiny/leash.
