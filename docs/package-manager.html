Package Manager

Overview

Every library lives in its own GitHub repository; the registry is an index.json that maps library names to repo URLs. The package manager is implemented natively in the self-hosted compiler (compiler/leashed.lsh) — there is no Python component. Publishing is fully self-service: a validation bot reviews and merges registry updates automatically, with no maintainer approval and no waiting on humans. The registry is also optional: you can install any library directly from its Git URL.

Quick start

Scaffold a library

Run leash pkg init mylib to create the standard project layout, then cd mylib.

Configure it

Edit leash-pkg.lshc: set the name, version, author, description and entry point (see Package configuration).

Publish

Run leash pkg publish. Your source is checked, compiled, pushed to a GitHub repo, tagged and registered — a bot merges the registry update.

Install it anywhere

Use leash pkg install mylib globally, or leash pkg add mylib to declare and install a project dependency.

All commands are subcommands of leash pkg. Unless noted, they work from any directory; dependency-related commands operate on the current project (a directory containing leash-pkg.lshc or leash.lock).

Package configuration (leash-pkg.lshc)

leash pkg init creates the standard library structure with a package configuration file where you specify the library's name, version, author, and entry point.

leash pkg init mylib
cd mylib
mylib/
├─ src/
│   └─ main.lsh        # Library entry point
├─ leash-pkg.lshc     # Package configuration
└─ .gitignore
name: "mylib"
version: "0.1.0"
author: "your-github-username"
description: "The mylib library"
main: "src/main.lsh"
KeyRequiredMeaning
nameYesPackage name; must match [a-zA-Z_][a-zA-Z0-9_-]*
versionYesSemantic version (X.Y.Z, optional -prerelease)
authorYesYour GitHub login; binds the package to your identity
descriptionYesShort description stored in the registry index
mainYesLibrary entry point, e.g. src/main.lsh
global_installNoSingle-line map of command name to source path; installs host binaries in ~/.leash/bin
repoNoExisting GitHub repo URL to publish into instead of creating one
dependenciesNoProject dependencies (managed by leash pkg add / update / uninstall)

Shipping command-line tools

To ship command-line tools with your package, add a global_install field (single line, {name: src, ...} — sources must live under the main source tree). Installing the package compiles each entry to a host binary in ~/.leash/bin; uninstalling the package removes them again:

global_install: {lint: src/lint.lsh, fmt: src/fmt.lsh}

Linking to an existing repository

To link to an existing GitHub repo, add a repo field:

repo: "https://github.com/you/mylib.git"

Project config.lshc keys

Separate from a library's leash-pkg.lshc, every application project has a config.lshc that controls builds. The build, run and install commands read it from the current directory. A generated file looks like this:

main: "src/main.lsh"
clibs: {}
imports: "imports/"
opt_level: "O3"
out_name: "myprogram"
autofree: false
gc: false
arena: true
KeyExampleMeaning
main"src/main.lsh"Entry point of the project
clibs{}External C libraries to link
imports"imports/"Local import search directory
opt_level"O3"Optimization level used by the build
out_name"myprogram"Name of the generated binary
global_install{tester: src/main_test.lsh}Tools built into ~/.leash/bin by leash install
autofreetrueCompile-time automatic frees, no GC runtime; also disables the arena
gc: true newtrue / yes / 1Opt back into the mark-and-sweep garbage collector instead of the default scoped arena. Equivalent to passing --gc.
arena: false newfalse / no / 0Disable the scoped bump arena when it is on by default. The arena is the default native layout; gc: true and autofree: true both turn it off as well.
Memory modes are exclusive. Do not combine gc: true, --no-garbage-collector and autofree: true. The JVM target always uses its own GC and ignores native memory-layout choices. See Advanced Topics for the full semantics of each mode.

Publishing a package

From inside your project directory, publish your library to the central registry. The publish command handles everything from verification to registration, making it easy to share your libraries with the community.

leash pkg publish

Verify

Your source code is checked with leash check.

Compile

Your library is compiled to a static .lib / .a file.

Create the repo

A GitHub repo is created under your account (if no repo is set) via gh repo create.

Push & tag

The source and compiled library are pushed to your repo and tagged v<version>.

Register

If you are the registry owner, the update is pushed directly to index.json; otherwise a fork opens a pull request that a validation bot merges automatically, usually within a minute. No human review is required.

Prerequisites. Requires GitHub CLI (gh) installed and authenticated (gh auth login), and Git installed.

Publishing rules

The registry bot enforces the same checks locally before anything is pushed, so mistakes fail fast:

  • You can only publish packages under your own GitHub login (the entry's publisher must match)
  • Only the original owner can update an existing package — names cannot be hijacked
  • Versions follow semantic versioning (X.Y.Z, optional -prerelease) and each publish must be strictly greater than the last
  • All previously published versions stay installable forever

Semantic versioning

Every release is tagged as v<version> in the library's repository and recorded in the registry's version history. Republishing requires bumping the version in leash-pkg.lshc:

version: "1.2.0"

Pre-release versions are supported and ordered correctly (1.0.0-rc.1 < 1.0.0):

version: "1.0.0-beta.2"
ChangeVersion bumpExample
Fixes that do not break compatibilityPatch1.2.0 → 1.2.1
Backward-compatible featuresMinor1.2.0 → 1.3.0
Breaking API changesMajor1.2.0 → 2.0.0
Pre-release of an upcoming versionSuffix1.0.0-beta.2, 1.0.0-rc.1

Lockfile: reproducible builds (leash.lock)

leash pkg maintains a per-project leash.lock file recording the exact resolved versions of the project's dependencies. Even though the object-file cache already skips recompiles for unchanged sources, the lockfile is what makes a project build identically on a fresh machine (or in CI) without any waiting or guesswork.

{ # leash.lock
  "version": 1,
  "packages": {
    "mylib": { "version": "1.2.3", "repo": "https://github.com/you/mylib.git", "tag": "v1.2.3", "rev": "a1b2c3d4e5f60718293a4b5c6d7e8f90a1b2c3d4" }
  }
}
FieldMeaning
versionLockfile format version (currently 1)
packagesMap from package name to its pinned entry
entry.versionExact semantic version installed
entry.repoRepository URL the package came from
entry.tagVersion tag in the repository (v + version)
entry.rev40-character commit SHA the tag resolved to

Rules of the lockfile

  • Write it once, commit it: leash pkg lock resolves leash-pkg.lshc's dependencies field, installs each package, and writes the lock. The file is meant to go into version control.
  • Fresh environments restore exactly: inside a project, bare leash pkg install (no target) restores the pinned versions from leash.lock — no re-resolution, no surprises.
  • Lockfile pins win: inside a project, leash pkg install (with a target) prefers the locked version when it exists.
  • Strict CI mode: leash pkg install --locked fails when a package is not pinned in leash.lock (or when no lockfile is present), instead of silently resolving another version.
  • Kept in sync: leash pkg add, leash pkg update and leash pkg uninstall update the lockfile automatically.
  • Revision pins: each entry also records the tag's commit SHA (rev). Restores verify it and abort on a moved tag, so a re-pointed tag can never silently change your build.
git clone myapp && cd myapp    # fresh clone
leash pkg install              # installs exactly leash.lock's versions

leash pkg lock                 # (re)write the lockfile from dependencies
leash pkg install --locked     # CI: fail on un-pinned dependencies

Registry protocol

Installing libraries

Install a library globally so any Leash program can use it. The installer fetches the registry, finds the library's repository, clones it, and places the files in the global libraries directory — no manual configuration needed. Inside a project directory (one containing a leash-pkg.lshc or a lockfile), installs are additionally recorded into leash.lock.

leash pkg install mylib

# Install a specific published version
leash pkg install mylib@1.2.3

This process:

  1. Fetches the registry index.json from raw.githubusercontent.com (no clone needed for the registry itself)
  2. Looks up the library name and finds its repo URL
  3. Shallow-clones only the library's repository (efficient, no history; at the requested version tag if given)
  4. Copies the files to ~/.leash/libs/<name>/
  5. Creates a stub <name>.lsh so use mylib::*; resolves correctly

Installing without the registry

The registry is only for discovery — any Git repository works as a package source. This is useful for private libraries, testing unpublished work, or when you don't want to wait for (or use) the central index:

# Full git URL
leash pkg install https://github.com/someone/somelib.git

# GitHub shorthand (equivalent to the URL above)
leash pkg install someone/somelib

The repo needs either a published library/ layout or a package.lshc / .lsh sources at its root.

Adding dependencies to a project

Add a library as a dependency of the current project. This is the standard way to declare and manage project dependencies — it installs the library, records the dependency in your package config, and sets up the import automatically.

leash pkg add mylib

This process:

  1. Installs the library globally if not already installed
  2. Appends mylib@version to the dependencies field in leash-pkg.lshc
  3. Inserts use mylib::*; into your main source file

Managing libraries

leash pkg list               # show installed libraries and versions
leash pkg info mylib         # registry metadata, all published versions
leash pkg install mylib      # install globally (pinned version inside a project)
leash pkg install            # inside a project: restore from leash.lock
leash pkg lock               # resolve dependencies and write leash.lock
leash pkg uninstall mylib    # remove an installed library (and unpin it)
leash pkg update             # update every dependency of the current project
leash pkg update mylib       # reinstall one library at its latest version

Searching for libraries

Search the registry for libraries by name or description. The search is efficient because it only fetches the lightweight index.json file — no cloning of individual library repositories is needed until you decide to install one.

leash pkg search math

The index.json format

Each library has its own GitHub repository. The central registry (foksiny/leash-packages) is an index.json file:

{
  "libraries": {
    "mylib": {
      "repo": "https://github.com/you/mylib.git",
      "description": "The mylib library",
      "author": "you",
      "publisher": "you",
      "version": "1.2.0",
      "versions": {
        "1.2.0": { "repo": "...git", "tag": "v1.2.0", "published_at": "2026-08-22T12:00:00Z" },
        "1.1.0": { "repo": "...git", "tag": "v1.1.0", "published_at": "2026-06-01T12:00:00Z" }
      }
    }
  }
}

The top-level fields always describe the latest version; the versions map keeps every release ever published so old versions remain installable.

Global library installation

Leash also provides a lower-level install command on the leash CLI to copy library files into ~/.leash/libs/ without the package manager.

Installing a single file

leash install path/to/mylib.lsh

Installing a directory

leash install path/to/mylib_folder/

The contents of the directory are copied directly into ~/.leash/libs/. The top-level folder name is not preserved.

For example, given:

mylib_folder/
├─ hash.lsh
└─ utils/
    └─ string_helpers.lsh

After installation, ~/.leash/libs/ contains:

~/.leash/libs/
├─ hash.lsh
└─ utils/
    └─ string_helpers.lsh
If a file or directory with the same name already exists in the global libs directory, the installation will fail. Remove the existing library first to replace it.

Frequently asked questions

QuestionAnswer
Do I need a Python tool to publish?No. The package manager is written natively in the self-hosted compiler; there is no Python component.
Is registry approval required?No. A validation bot re-checks every rule and auto-merges clean pull requests, usually within a minute.
Can I install private packages?Yes — install from a full Git URL or a user/repo shorthand without touching the registry.
Why commit leash.lock?It pins exact versions and commit SHAs so fresh clones and CI builds are identical and protected against moved tags.
What does leash pkg add change?It installs the library, appends name@version to dependencies, inserts use name::*; in the main source, and updates the lockfile.
Can I ship executables with a library?Yes — add global_install: {name: src/path.lsh, ...}; installs build binaries into ~/.leash/bin.
How do I opt out of the arena in a project?Set gc: true or arena: false in config.lshc (or pass --gc on the command line).
