Leash 2.4.3

Self-Hosted Compiler

Overview

Since the 1.0 release, the shipped leash compiler is written in Leash. Its sources live in compiler/*.lsh: tokens.lsh, ast.lsh, lexer.lsh, parser.lsh, typechecker.lsh, optimize.lsh, codegen.lsh, driver.lsh and main.lsh. It emits LLVM IR text and links against the same Leash runtime/GC (leash/gc.c) through clang.

The self-hosted compiler is a 1:1 replica of the original Python reference compiler across the whole example corpus: 89/89 programs compile and run with identical output. The corpus was recorded from the original reference compiler; entries added after it was retired are recorded from the current self-hosted compiler. It implements the entire toolchain natively — compile, run (file and project modes), check, dump, init, build, install, update, pkg, self-host, and the interactive dbg debugger. The Python reference compiler has been retired; the self-hosted compiler is the only toolchain and the repository contains no Python in the build or run path.

Bootstrap pipeline

Bootstrapping is a three-stage process that ends when two consecutive compiler generations produce textually identical IR. The seed is trusted once; every later stage is a program the previous stage compiled itself.

StageActionOutput
Stage 0The checked-in seed binary (bootstrap/leash-<version>-target-*) builds compiler/main.lsh. No Python involved.bin/leashc_stage1
Stage 1leashc_stage1 compiles compiler/main.lsh.bin/leashc_stage2
Stage 2leashc_stage2 compiles compiler/main.lsh.bin/leashc_stage3
Fixed pointStage 2 IR and Stage 3 IR must be textually identical (modulo comments/whitespace).bin/leashc

          │  compiles compiler/main.lsh

  leashc_stage1  ── compiles ──>  leashc_stage2

                                       ▼
                                  leashc_stage3
                                       │

                                       │

Fixed point

The fixed-point check is a hard gate, not a warning. If the IR emitted by Stage 2 and Stage 3 differs after normalizing comments and whitespace, the bootstrap fails and no bin/leashc is installed. This catches compiler regressions that would otherwise compound across generations — a change that alters codegen changes the compiler that performs the next codegen, so the pipeline must stabilize before it is trusted.

Why three stages? Stage 1 proves the seed can compile the compiler. Stage 2 is the first self-compiled generation. Stage 3 is what Stage 2 produces; comparing the last two generations verifies the compiler reproduces itself exactly.

Building it

Get a checkout

Clone the repository and make sure clang is on your PATH. On a Linux x64 or macOS host the checked-in seed matches automatically.

Run the bootstrap

From the repository root, run bash scripts/bootstrap.sh, or use the compiler's own command, leash self-host.

Watch the fixed-point check

The pipeline runs Stage 0–2 and diffs the Stage 2 and Stage 3 IR. A mismatch aborts the install with a diagnostic.

Use the result

On success bin/leashc is installed as the official self-hosted compiler. Installing the package already performs Stage 0 plus one self-compilation, so a fresh install is bootstrapped out of the box.

# Full pipeline from a repository checkout
bash scripts/bootstrap.sh

# Equivalent native command
leash self-host

Commands

# Compile to a native binary and run it

Parity and verification

The self-hosted frontend covers the full language: primitives, pointers, references, arrays, slices, vec<T>, matrix<T>, hash<K,V>, structs, classes (instance and static methods and fields, vtables, inheritance), enums, unions, generics (class<T>, def T : template, multi-type [int, float, ...] parameters with monomorphization), opdef operator overloading, error/throw, big integers (int<N>/uint<N> up to 512 bits), async/await futures, the File API, lambdas, tuples, macros, and the string-interpolated show family including buffered showb.

scripts/ir_diff.py

The parity harness: runs every example under both compilers and compares outputs. Result: 89/89 exact match, 0 mismatches, 0 compile failures.

scripts/bootstrap.sh / leash self-host

The three-stage bootstrap with a hard fixed-point check between the last two generations.

tests/test_self_hosted.py

The compiler test suite: python3 -m unittest tests.test_self_hosted.

Together these give three independent signals: the corpus proves behavioral equivalence, the fixed point proves codegen stability, and the unit suite exercises compiler internals directly. A regression generally fails at least one of them before it reaches a release.

Troubleshooting

SymptomLikely causeFix
clang: command not foundNo C compiler on PATH.Install LLVM/clang and verify clang --version before bootstrapping.
Seed binary will not executeWrong platform seed, or missing execute permission.Use the bootstrap/leash-<version>-target-* matching your OS/architecture and ensure it is executable.
Fixed-point check failsCodegen changed between stages, often from an uncommitted compiler edit.Start from a clean checkout, confirm both stages use the same runtime, and rebuild. A genuine IR difference is a compiler bug — capture the diff.
Parity harness reports mismatchesA frontend or codegen change altered program output.Run scripts/ir_diff.py to isolate the example, then bisect the compiler change.
bin/leashc is staleAn earlier successful bootstrap left an old binary in place.Remove bin/leashc_stage* and rerun leash self-host.
Tests cannot find modulesWrong working directory for the test command.Run python3 -m unittest tests.test_self_hosted from the repository root.

FAQ

Is Python still part of the build?

No. The Python reference compiler is retired and there is no Python in the build or run path. Python is only used by the verification harnesses and unit tests, which are development tools.

What does installing the package actually do?

It bootstraps the compiler: Stage 0 plus one self-compilation. Running leash self-host from a checkout performs the full Stage 0–2 pipeline, the fixed-point diff, and installs bin/leashc.

Why keep a checked-in seed at all?

Every bootstrap needs a trusted starting point. The seed is compiled once and then verifies itself by reaching a fixed point, so no external compiler implementation is needed afterward.

Does the self-hosted compiler support the JVM target?

Yes. The JVM backend is emitted by the self-hosted compiler only (bin/leashc): it writes .class files directly, with no clang or linking step. See the Compiler & CLI page for the supported JVM surface.

What happens to the 89/89 corpus as the language grows?

The original corpus was recorded from the reference compiler. Entries added after its retirement are recorded from the current self-hosted compiler, so the harness keeps a stable byte-for-byte expectation for every program in it.

Bootstrapping is a normal part of development, not a rare ritual. If a change touches the frontend or codegen, rerun the bootstrap and the parity harness before shipping — the fixed point is the cheapest way to know the compiler still reproduces itself.
